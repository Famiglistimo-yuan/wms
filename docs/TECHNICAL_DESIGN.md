# JavaFX + Spring Boot 仓库管理系统（客户机/服务器版）技术方案

## 一句话描述

以 JavaFX 构建跨平台桌面客户端、以 Spring Boot 构建 Web 服务端，通过 HTTP + JSON 通信的客户机/服务器（C/S）架构仓库管理系统，满足《应用软件开发》课程开发课题三的全部必选与可选功能要求。

## 1. 项目背景与课题要求

### 1.1 课题定位

本方案对应《应用软件开发》课程开发课题三「仓库管理系统开发——客户机/服务器版」。课题功能与课题二（桌面版）完全相同，技术要求更高：子系统 1-3 以桌面程序实现，桌面程序通过 HTTP 与后台 Web 服务器通信，数据库操作全部由 Web 服务器完成，**客户端不得持有数据库账号密码**。

### 1.2 课题硬性要求清单

| 编号 | 要求 | 本方案应对 |
|------|------|-----------|
| R1 | 子系统 1-3 以桌面程序（Windows 窗体程序）实现 | JavaFX 桌面客户端，打包为 Windows 可执行程序 |
| R2 | 桌面程序以 HTTP 方式与后台 Web 服务器通信 | RESTful HTTP + JSON，Spring Boot 内嵌 Tomcat |
| R3 | 数据库操作由 Web 服务器实现 | 持久层全部位于服务端，客户端仅调用接口 |
| R4 | 客户端不得使用数据库用户名和密码 | 客户端代码零 JDBC 依赖，数据库凭证仅存于服务端配置 |
| R5 | 通信可选用 RSA 加密 | 预留 RSA 加密通道（选做），支持 HTTPS 部署 |
| R6 | 修改业务逻辑不需要用户重装客户端 | 业务逻辑收敛于服务端，客户端仅负责界面与交互 |
| R7 | 不得设计成 B/S 模式 | 客户端为独立桌面进程，非浏览器访问 |
| R8 | 服务器端将数据库账号密码保存到配置文件中（需求 AR-6） | 凭证仅存于服务端 `application-local.yaml`（不入库），由 R4 一并覆盖 |
| R9 | 后台 WEB 服务器使用 TOMCAT（需求 AR-8，页 7 点名） | Spring Boot 内嵌 Tomcat 10.1（见 §3 技术栈表） |

### 1.3 功能范围（继承课题二）

| 子系统 | 功能要点 |
|--------|---------|
| 子系统一 | 人员档案管理、物料档案管理（增删改查、正则校验、日期控件、模糊查询） |
| 子系统二 | 单物料进仓/出仓（单号自动生成、库存校验、事务控制） |
| 子系统三 | 多物料进出仓（一单多料、同进同出、失败整体回滚） |
| 子系统四 | 用户登录与权限管理（口令加密存储、按权限显隐菜单、可扩展授权） |
| 子系统五 | 统计与报表（进出仓流量统计、月度进出仓单、仓库账本、导出 PDF/Excel） |
| 补充功能 | 自动升级（版本检测、下载替换、重启） |

## 2. 架构全景

### 2.1 总体架构

系统采用经典三层 C/S 架构，客户端与服务端完全解耦，以接口契约（REST API）为唯一耦合点：

```
┌─────────────────────────────────────────────────────┐
│           桌面客户端（JavaFX 21）                     │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌──────────┐   │
│  │ 档案管理 │ │ 进出仓   │ │ 权限/登录│ │ 报表/升级 │   │
│  └─────────┘ └─────────┘ └─────────┘ └──────────┘   │
│         视图层 FXML + Controller（无业务逻辑）        │
│  HTTP 客户端层：HttpClient + JSON 反序列化 + JWT 携带  │
└───────────────────┬─────────────────────────────────┘
                    │ HTTP + JSON（REST，8080 端口）
                    │ Authorization: Bearer <JWT>
┌───────────────────▼─────────────────────────────────┐
│           Web 服务端（Spring Boot 4.0.8，内嵌 Tomcat）  │
│  ┌──────────────────────────────────────────────┐   │
│  │ Controller 层：参数校验、DTO 转换、统一响应     │   │
│  │ Service 层：业务逻辑、调用存储过程（事务在SP）  │   │
│  │ Mapper 层（MyBatis-Plus）：SQL 与ORM 映射      │   │
│  └──────────────────────────────────────────────┘   │
│  横切：全局异常处理 / JWT 鉴权过滤器 / 日志 AOP       │
└───────────────────┬─────────────────────────────────┘
                    │ JDBC（HikariCP 连接池）
┌───────────────────▼─────────────────────────────────┐
│           MySQL 8.x 数据库                           │
│  人员表 / 物料表 / 进出仓单表 / 明细表 / 用户权限表    │
└─────────────────────────────────────────────────────┘
```

### 2.2 核心请求链路（以多物料出仓为例）

```
用户在界面录入出仓单（物料列表）
  → 客户端 POST /api/stock/orders，JSON 请求体携带明细数组
  → 服务端 JWT 过滤器校验身份与权限
  → Controller 接收 DTO，参数校验
  → Service 组装参数调用存储过程：SP 内校验库存 → 扣减 → 写入单据与明细
  → 任一步失败 SP 内回滚并返回失败原因 → 服务端转统一错误响应
  → 全部成功 SP 内提交 → 返回成功响应
  → 客户端解析响应，弹窗提示成功/失败原因
```

## 4. 核心设计决策（ADR）

### ADR-001：客户端框架选择 JavaFX

- **状态**：已采纳
- **上下文**：团队为 Mac/Windows 混合开发环境，全员 Java 背景，正在系统学习 Spring Boot。课题要求桌面程序，且期末答辩由主观打分，方案争议越小越好。
- **候选方案对比**：

| 维度 | JavaFX | Electron | C# WinForms |
|------|--------|----------|-------------|
| 满足"桌面程序"要求 | 完全满足 | 打擦边球（HTML 渲染，答辩需自证） | 完全满足且最贴合原文 |
| Mac 上开发调试 | 原生支持 | 原生支持 | 不支持，需虚拟机 |
| 与团队技术栈契合 | 全 Java，DTO 复用 | 需引入 JS/TS 生态 | 全员转 C# |
| 学习成本 | 低（同语言） | 中高 | 中 |
| 界面开发效率 | 中（Scene Builder） | 高 | 高 |
| 自动升级 | 需自研（简单） | electron-updater 开箱即用 | 需自研或 ClickOnce |

- **决策**：采用 JavaFX 21 LTS。
- **理由**：唯一同时满足「桌面程序无争议 + Mac/Win 双平台开发 + 零语言切换成本」的选项；Electron 的界面效率优势不足以抵消答辩争议风险与生态引入成本。
- **后果**：界面美观度上限低于 Web 技术（用 CSS 可弥补大部分）；自动升级需自行实现（约一天工作量，方案见 §7.5）。

### ADR-002：通信协议采用 REST + JSON

- **状态**：已采纳
- **上下文**：课题考核点明确包含「网络通信：加密与否、数据封装效率，XML、JSON、字符串」的对比分析。
- **候选方案对比**：

| 维度 | JSON | XML | 自定义字符串 |
|------|------|-----|-------------|
| 传输体积（同一批数据） | 基准 | 约 1.3~1.8 倍 | 最小 |
| 可读性/调试便利 | 好 | 好 | 差 |
| 解析库生态 | Jackson 一行搞定 | 需处理节点树 | 手写解析器，易出错 |
| 字段自描述 | 有 | 有 | 无 |
| 与 Java 对象映射 | 直接映射 DTO | 需注解配置 | 手动拼装 |

- **决策**：REST + JSON 为主协议。
- **理由**：体积、可读性、开发效率三者平衡最优；自定义字符串仅在报告性能对比小节中作为实验基线出现，不用于生产代码。
- **后果**：报告中可附一份「同一批进出仓数据三种封装的字节数对比」实测数据，直接命中考核点。

### ADR-003：鉴权采用 JWT 无状态令牌

- **状态**：已采纳
- **上下文**：客户端是独立桌面进程而非浏览器，传统 Session 方案需处理 Cookie 跨域与桌面端存储，且 C/S 架构下服务端保持无状态更利于考核点「可扩展性」的论述。
- **决策**：登录成功后服务端签发 JWT（含用户 ID、权限摘要、过期时间），客户端存储于本地文件并在每次请求的 `Authorization` 头携带；服务端过滤器统一校验。
- **后果**：令牌注销需依赖短过期时间 + 服务端黑名单（演示级实现可不加黑名单，报告中说明取舍）。

### ADR-004：并发扣库存采用数据库乐观锁

- **状态**：已采纳
- **上下文**：课题考核点「多用户并发冲突处理：同一功能多个用户同时使用时是否会出现问题」——多个用户同时对同一物料出仓时，简单「读库存 → 判断 → 更新」会产生超卖。
- **候选方案对比**：

| 维度 | 乐观锁（条件更新） | 悲观锁（SELECT ... FOR UPDATE） | 分布式锁 |
|------|------------------|-------------------------------|---------|
| 实现复杂度 | 一条 SQL | 需事务包裹，锁范围控制 | 引入 Redis，过重 |
| 冲突低时性能 | 优 | 中 | 差 |
| 冲突高时 | 需重试 | 稳定 | 稳定 |
| 课程场景适配 | 最优 | 可行 | 杀鸡用牛刀 |

- **决策**：扣减库存使用条件更新语句 `UPDATE material SET stock = stock - #{qty} WHERE id = #{id} AND stock >= #{qty}`（置于存储过程内执行），影响行数为 0 即判定库存不足，事务回滚并返回明确错误信息。
- **后果**：单条 SQL 即原子完成「校验 + 扣减」，天然防超卖；答辩时可现场演示两个客户端并发出仓同一物料的冲突场景。

### ADR-005：业务逻辑全部收敛于服务端

- **状态**：已采纳
- **决策**：客户端只做「界面渲染 + 输入校验 + 接口调用」，一切业务规则（库存校验、单号生成、权限判断、事务控制）都在服务端实现。
- **理由**：直接满足课题 R6（改业务逻辑不用重装客户端）与 R4（客户端无数据库凭证）；答辩讲解分层架构时论据清晰。

### ADR-006：进出仓共用一组「主表＋明细」表

- **状态**：已采纳
- **上下文**：课题 FR-2-10 明确「进出仓表可用一个表或两个表，表设计思路须在报告中描述」；FR-3 又要求一个单号对多种物料同进或同出（一单多料），且同单号日期、操作人完全一致、不能进出混存（FR-3-4/3-5）。
- **候选方案对比**：

| 维度 | A 进/出仓各一套表 | B 共用主表＋明细、类型字段区分（已选） | C 单张平表不拆主明细 |
|------|------------------|--------------------------------------|---------------------|
| 一单多料（FR-3） | 各自配明细表可支撑 | 明细表支撑 | 无法支撑，直接出局 |
| 统计报表（FR-5） | 流量/账本需 UNION 两套表 | 按类型字段一条 GROUP BY | 同左且字段冗余严重 |
| 代码/SP 复用 | 进、出各写一遍 | 一套 SP/Service，方向只是参数 | 最少但不可行 |
| 同单同向（FR-3-5） | 物理隔离天然满足 | 主表类型字段 CHECK 兜底 | 只能靠应用层判断 |
| 表数量与维护成本 | 翻倍 | 基准 | 最少 |

- **决策**：方案 B——进出仓共用 `wms_stock_order`（主表）＋ `wms_stock_order_item`（明细），主表 `order_type`（IN/OUT）区分方向；「主/明细拆分」是为一单多料，与「进/出是否分表」是两个正交问题。
- **理由**：单物料进出仓（FR-2）只是明细长度为 1 的特例，两套课题要求共用同一实现；报表聚合与存储过程均只维护一份；方案 A 的物理隔离在课程场景收益为零，代价是全部查询与逻辑翻倍。
- **后果**：DDL 已按此落地（`docs/sql/schema.sql`，MySQL 8.4 实测建库通过）；报告「进出仓表设计思路」章节直接引用本 ADR；方向合法性由 CHECK 约束兜底，业务校验在存储过程内完成。

### ADR-007：客户端界面形态采用「单窗口切换 ＋ Dialog」

- **状态**：已采纳
- **上下文**：课题 FR-1-1 要求「主界面可以通过菜单调用到其它所有子程序」，阶段 2 三人并行开发各自的子系统界面，需先统一窗口形态（候选：主界面内切换单窗口 vs 每个子程序独立顶层窗口），避免各写一套导航。
- **候选方案对比**：

| 维度 | A 单窗口切换＋Dialog（已选） | B 子程序独立窗口 |
|------|------------------------------|------------------|
| 编辑后列表刷新 | 同一场景树内重查/回填即得 | 需窗口间通信（回调/监听），每对窗口一套胶水 |
| 窗口管理成本 | 零（复用 primaryStage） | 每窗 initOwner/initModality/关闭处理 |
| 三人并行冲突面 | 共享点仅 App.showPanel 注册，每人约 1 行 | 窗口工厂＋刷新协议需全组约定 |
| 「程序名」承载（CONTRIBUTING §5.1） | 满足：每功能仍有独立前缀 FXML＋Controller | 满足 |
| 演示形态 | 集中，管理后台风格 | 多窗口层叠，投影易乱 |

- **决策**：方案 A——全客户端单一顶层窗口：菜单点击经统一的 `App.showPanel(fxmlName)` 在主界面 center 区切换子程序面板；「记录定位 → 修改」等二级交互用 `Dialog`/`Alert` 承载（`showAndWait` 取结果后由调用方刷新列表），不新建顶层 Stage。每个功能仍对应独立的 `rg2402_11_12_13_*.fxml` ＋ Controller，「程序名」承载不变。
- **理由**：CRUD 应用核心循环是「列表 → 编辑 → 列表」，A 的数据刷新天然一致；排期无缓冲，A 的样板代码最少；B 的解耦优势可用轻量路由约定补齐，其窗口间刷新成本却无法用约定消除。
- **后果**：`App.showPanel` 是全组共享的导航入口，阶段 2 各界面骨架从该模板复制；二级表单一律 Dialog，确需独立顶层窗口时先在组内说明；本对比直接用于报告「复杂问题多方案比较择优」章节。

### ADR-008：升级包为「固定名 fat jar」，Updater 复用主程序自带 runtime

- **状态**：已采纳
- **上下文**：FR-6 自动升级（方法二）需明确「下载并替换」的对象与方式。约束有三：① jpackage 启动配置 `WMS.cfg` 将 classpath 文件名写死于打包时刻；② wms-common 作为两端共享模块会持续演进（VersionInfo 等契约 DTO 随 FR-4/FR-5 落地），仅替换主 jar 时其旧版本仍留在 app/ 目录；③ 用户机器不装 Java，Updator 自身也需要运行环境。
- **候选方案对比**：

| 维度 | A 主 jar 固定名 fat jar（已选） | B 主 jar 带版本号 | C 整包 zip 覆盖 | D msi 静默重装 |
|------|-------------------------------|------------------|----------------|---------------|
| 升级后可启动性 | ✓（cfg 的 classpath 名不变） | ✗ cfg 找不到新文件名，新版起不来 | ✓ | ✓ |
| 共享模块（wms-common）演进 | 随 fat jar 一并升级 | 同左 | 随整包 | 随整包 |
| 贴合课题「下载主程序文件并替换」 | ✓ 单文件 | ✓ | ✗ 更近重装 | ✗ 重装 |
| 演示直观性 | 换一个文件即完成 | — | 覆盖大量文件 | msiexec 细节多 |
| Updater 运行环境 | 复用 app-image 自带 runtime | — | 需自带 | 需自带 |

- **决策**：主 jar 用 maven-shade 打成 fat jar（打入 wms-common 与 Jackson 等纯 Java 依赖、**排除 JavaFX**——含 native lib 平台相关且不随升级变更，由 app/ 目录提供），**固定文件名 `wms-client.jar`**；版本号由 jar 内 `version.txt`（打包期注入）承载，jpackage 的 `--app-version` 由打包脚本参数传入。Updater 由主程序用 `appRoot/runtime/bin/java` 启动，免二次 jpackage。
- **理由**：固定名是「升级后能启动」的硬约束（cfg 不随升级更新）；fat jar 是「只换一个文件就能完成升级」的前提（共享模块与业务代码依赖版本随主 jar 走，杜绝新旧混载的 ClassNotFoundException）；复用 runtime 让用户机器彻底免装 Java。
- **后果**：**升级粒度**——业务代码、wms-common 契约 DTO、Jackson 等纯 Java 依赖随主 jar 升级；JavaFX 及其 native lib 不随升级变更，需整包重装（报告说明此边界）。打包脚本负责把已被 shade 的坐标从 `dependency:copy-dependencies` 平铺产物中剔除，避免 app/ 目录同时存在「主 jar 内嵌版本」与「独立 jar 版本」造成类加载二义性。.bak 备份滚动保留一个版本，回滚为手动改名。

## 5. 数据库设计

### 5.1 表清单

按课题命名规范，所有表名以「班级＋座号」为前缀。本组前缀为 **`rg2402_11_12_13_`**（实体 `@TableName` 直书完整表名——MP 的 `table-prefix` 对显式 `@TableName` 不生效，项目不配置，见 docs/CONTRIBUTING.md §7.2 口径）；下表以 `wms_` 简写代替实际前缀以便阅读；**完整可执行 DDL 与存储过程签名契约以 `docs/sql/schema.sql` 为准**（MySQL 8.4 实测建库通过）：

| 表名 | 用途 | 关键字段 |
|------|------|---------|
| `wms_person` | 人员档案 | id、人员代码(唯一)、姓名、性别、出生日期、身份证号、籍贯、住址、电话 |
| `wms_user` | 登录用户 | id、人员代码(外键)、用户名、口令(BCrypt 密文，**varchar(60)**——BCrypt 固定输出 60 字符，参考样本设 varchar(20) 会截断失效)、状态（口令独立成表而非挂在人员表，等价满足需求 FR-4-1，答辩口径：口令仍属人员数据，拆表仅为登录职责分离） |
| `wms_role` / `wms_permission` | 角色/权限（菜单项资源） | 权限编码对应菜单项标识 |
| `wms_user_role` / `wms_role_permission` | 授权关系表 | 多对多，支撑「可对后续新增权限管理而无需改代码」 |
| `wms_material` | 物料档案 | id、物料代码(唯一)、名称、规格型号、计量单位、库存数量(非负约束)、备注 |
| `wms_stock_order` | 进出仓单主表 | 单号(唯一)、日期、类型(进/出)、操作人、经手人、备注 |
| `wms_stock_order_item` | 进出仓单明细 | 单号(外键)、物料代码、数量 |

### 5.2 设计要点

1. **主表 + 明细表**拆分支撑子系统三「一单多料」：同一单号的多条明细共享主表的单号、日期、操作人，且类型字段保证同单号不混进混出。
2. **单号生成规则**：服务端生成，格式 `类型前缀 + yyyyMMdd + 4 位当日流水号`（如 `IN202609080001`），流水号用数据库序列或 `SELECT ... FOR UPDATE` 保证并发下不重复，规则在报告中说明（课题要求）。
3. **索引**：`wms_material(物料代码)`、`wms_material(名称)`、`wms_stock_order(日期, 类型)`、`wms_stock_order_item(单号)` 建索引；姓名/物料名模糊查询前缀匹配场景可走索引，报告中说明 `LIKE '%x%'` 不走索引的取舍。
4. **约束兜底**：库存数量列加 `CHECK (stock >= 0)`，作为乐观锁之外的最后一道防线（需 MySQL ≥ 8.0.16，更低版本会静默忽略 CHECK）。
5. **存储过程**：课题原文（课题二子系统二/三）**硬性要求**进出仓通过存储过程实现（FR-2-8 / FR-3-6），本方案**以存储过程为默认实现**——事务提交/回滚、物料存在与库存非负校验、乐观锁（`WHERE stock >= ?` 或 version 列）均在 SP 内完成，锁与事务不分离；Java 侧通过 MyBatis XML mapper 的 `CALL` 语句调用。应用层 `@Transactional` 版本仅作为报告对比素材——说明「事务边界在应用层 vs 数据库层」的优劣，转化为答辩加分项。
6. **库存一致性纪律（参考样本项目的反面教训，答辩可讲改进点）**：库存增减必须与单据的增/删/改在**同一事务**内冲正——删除或修改单据时同步回滚/调整库存；**禁止用触发器维护库存**（触发器只覆盖 INSERT，删单即漏，样本项目正犯此错）。无论最终用应用层事务还是存储过程，课题要求的两项校验——物料存在、库存非负——必须真实生效并返回明确失败信息（样本的存储过程校验形同虚设，不可效仿）。

### 5.3 权限模型（RBAC）

```
用户 ──< 用户角色 >── 角色 ──< 角色权限 >── 权限(菜单项)
```

- 每个菜单项即一个权限资源，编码如 `menu.material.add`。
- 登录后服务端返回该用户的权限编码集合，客户端据此显隐/禁用菜单项（无权菜单不可见）。
- 新增功能菜单 = 权限表插一行 + 授权界面配置，**无需修改子系统四代码**（课题明确要求）。

## 6. REST 接口设计

### 6.1 统一响应格式

```json
{
  "code": 0,
  "message": "success",
  "data": { }
}
```

| code | 含义 |
|------|------|
| 0 | 成功 |
| 401 | 未登录 / 令牌过期 |
| 403 | 无权限 |
| 400 | 参数校验失败（message 说明具体字段） |
| 409 | 业务冲突（如库存不足、代码重复） |
| 500 | 服务端异常 |

> **HTTP 状态恒 200**：业务成败不在状态行表达，一律以响应体 `code` 为准（客户端统一解析
> body 后按 code 分流，网络层异常另行处理）。本节 code 为应用层业务码，数字沿用 HTTP
> 语义仅为可读性，与状态行无关。

### 6.2 接口清单（节选）

| 方法 | 路径 | 功能 |
|------|------|------|
| POST | `/api/auth/login` | 登录（公开），返回 JWT + 权限码集合 |
| GET | `/api/auth/me` | 当前用户信息+最新权限集（启动恢复校验+权限刷新；受保护） |
| POST | `/api/auth/logout` | 注销（语义入口，公开） |
| GET | `/api/persons?name={字}&page=&size=` | 人员分页查询（支持单字模糊） |
| POST/PUT/DELETE | `/api/persons` `/api/persons/{id}` | 人员增删改 |
| GET | `/api/materials?keyword=&page=&size=` | 物料分页模糊查询 |
| POST/PUT/DELETE | `/api/materials` `/api/materials/{id}` | 物料增删改 |
| POST | `/api/stock/orders` | 提交进出仓单（单物料/多物料同一接口，明细数组长度 ≥ 1） |
| GET | `/api/stock/orders?dateFrom=&dateTo=&material=&operator=&remark=` | 单据组合查询 |
| GET | `/api/stats/material-flow?from=&to=` | 物料流量统计（图表数据） |
| GET | `/api/reports/monthly-orders/{yyyyMM}` | 导出月度进出仓单 Excel |
| GET | `/api/reports/ledger/{materialCode}/{yyyy}` | 导出仓库账本 PDF |
| GET | `/api/users`；PUT `/api/users/{id}` | 用户查询/新增/修改（口令重置、启停用），需 `menu.auth.user` |
| GET/POST | `/api/users/{id}/roles` | 查询/分配用户角色（逐用户授权，全量覆盖），需 `menu.auth.grant` |
| GET | `/api/roles`；GET `/api/roles/permissions` | 角色列表（含权限码）/ 权限资源列表（菜单项） |
| GET/POST | `/api/roles/{roleId}/permissions` | 查询/分配角色权限（逐角色授权，全量覆盖），需 `menu.auth.grant` |
| GET | `/api/version` | 客户端版本检测（自动升级） |

### 6.3 设计约定

1. 分页统一 `page`（从 1 起）+ `size`（默认 20，上限 100）参数，响应携带 `total`。
2. 所有写操作以 DTO 接收，`@Valid` 注解 + `BindingResult` 输出字段级错误信息。
3. 报表导出接口返回文件流（`Content-Type: application/octet-stream`），客户端下载后用系统默认程序打开。
4. 接口文档用 SpringDoc（OpenAPI 3）自动生成，开发期浏览器查看，前后端联调以它为契约。

## 7. 关键功能实现方案

### 7.1 档案管理（子系统一）

- 身份证号校验正则：`^\d{17}[\dXx]$`（最后位数字或 X，课题明确要求正则验证）；用户名/口令格式校验同样用正则，在客户端与服务端双重校验。
- 性别用单选/下拉（男、女），出生日期用 `DatePicker` 控件（课题要求日期控件）。
- 人员查询支持「姓名中任意单字」：`WHERE name LIKE CONCAT('%', ?, '%')`。
- 物料计量单位：下拉可选（件、套、公斤、吨、升、米、毫米、个）+ 允许自定义输入，用可编辑 `ComboBox` 实现。
- 物料代码自动生成（可选规则）或手动输入，服务端唯一性校验，重复返回 409。

### 7.2 进出仓管理（子系统二、三）

- 单物料与多物料共用一条提交接口：明细数组长度为 1 即单物料场景，界面两个入口共用同一后端。
- 事务边界：默认走存储过程（§5.2 第 5 条），校验、条件更新扣库存、写单据均在 SP 内，任一步失败整体回滚；应用层 `@Transactional` 版本仅作报告对比素材。
- 操作人默认取 JWT 中的当前登录用户；经手人从人员档案下拉选择（课题要求）。
- 同一单号内「进/出」类型由主表单选决定，服务端校验同单不混类型。
- 单据删除与修改同样走存储过程，库存同步冲正（删单/改小→回补，改大→再扣），防止「只删单不改库存」。

### 7.3 权限管理（子系统四）

- 登录流程：客户端提交用户名口令 → 服务端 BCrypt 比对 → 签发 JWT（含权限码）→ 客户端按权限码渲染菜单，无权菜单 `setVisible(false)` 且 `setDisable(true)` 双保险。
- 授权界面：两级 RBAC——「角色 × 权限」勾选授予/收回 +「用户 × 角色」分配；用户实际权限 = 其全部角色的权限并集，操作仅影响对应角色/用户（RBAC 关系表天然满足，FR-4-3/4-6）。
- 服务端接口级鉴权：自定义注解 `@RequirePermission("menu.xxx")` + 拦截器校验——即使客户端被绕过，接口仍然安全（答辩论述纵深）。

### 7.4 统计与报表（子系统五）

- 流量统计：服务端聚合查询返回 JSON，客户端用 JavaFX 自带 `BarChart`/`LineChart` 渲染；分析流动量最小物料直接在统计结果中排序得出。
- 月度进出仓单：EasyExcel 生成，含报表头（标题行、生成时间、制表人）、表格边框、按单号排序。
- 仓库账本：给定年份 + 物料，按日期行列出进仓、出仓、结存，iText 输出 PDF。
- 两个文件导出（月度单、账本）均带报表头与边框，排版对照课题「规范的报表」样例自查。

### 7.5 自动升级（补充功能，分工必选项）

实现路线采用课题提示的方法二（独立升级程序），流程：

```
主程序启动 → GET /api/version 比对版本号
  → 版本一致：正常进入登录
  → 版本更新：弹窗提示 → 用户确认后启动 Updater.exe 并退出主程序
      → Updater 从服务端下载新版安装包（HTTP）
      → 校验文件 MD5 → 替换主程序文件 → 重启主程序 → Updater 退出
```

- 版本号与下载地址由服务端 `/api/version` 下发，服务端改动即可控制发布节奏。
- Updater 是一个不含业务逻辑的极小 Java 程序，单独打包；主程序被占用无法自替换的问题由「先退主程序再替换」解决。

**发布流程（运维视角）**：

1. `./mvnw versions:set -DnewVersion=x.y.z -DgenerateBackupPoms=false`（版本单一来源，`version.txt` 经 resources filtering 随之注入主 jar）
2. `./scripts/package-appimage.sh x.y.z`——产物 `target/jpackage/WMS.app`（Windows 同参数），末尾打印主 jar 的 MD5
3. 主 jar（固定名 `wms-client.jar`）拷入服务端 `static/download/`
4. 版本号与 MD5 填入 `application.yaml` 的 `wms-update` 块，重启服务端。客户端下次启动即检测到新版本

**升级包的替换粒度与文件名（实现约束，详见 ADR-008）**：主 jar 为 shade fat jar（含 wms-common 与 Jackson 等纯 Java 依赖）且**固定名 `wms-client.jar` 不带版本号**——jpackage 启动配置 `WMS.cfg` 写死 classpath 文件名，带版本号会导致升级后启动器找不到文件；版本信息由 jar 内 `version.txt` 承载。JavaFX 及其 native lib 不随升级变更（由打包的 `app/` 目录提供，升级需整包重装）。

### 7.6 RSA 加密通信（选做）

- 模式：服务端生成密钥对，公钥内置于客户端；敏感字段（登录口令）以 RSA 公钥加密传输，服务端私钥解密；令牌与普通业务数据仍走 JSON 明文。
- 生产替代：部署时启用 HTTPS（Spring Boot 配置 SSL 证书即可），报告中说明「传输层加密 vs 字段级加密」的适用场景对比。

## 11. 风险与边界

1. **JavaFX 界面美观度**：默认控件朴素，需投入统一 CSS 样式（`resources/styles.css` 全局美化）；接受「工整清晰」而非「炫酷」的定位。
2. **存储过程要求**：课题原文硬性要求进出仓走存储过程（FR-2-8 / FR-3-6），本方案**以存储过程为默认实现**（事务提交/回滚与乐观锁均在 SP 内，锁与事务不分离），应用层事务版本仅作为报告中的方案对比素材（§5.2 第 5 条）。
3. **RSA 选做的工期风险**：优先级排在所有必选功能之后，第 6 周仍未有余力则只保留 HTTPS 部署演示。
4. **打包只限 Windows**：jpackage 不支持交叉编译，最终打包绑定在 Windows 成员机器；打包预演提前到骨架期完成一次，避免期末单点故障。
5. **适用边界**：本方案面向课程场景（2-3 人团队、单库单服务、几十并发以内）；若扩展到真实生产（高并发、多仓库、云端部署），需引入网关、缓存与消息队列，报告中作为「可扩展性」讨论素材。
