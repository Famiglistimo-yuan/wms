# 仓库管理系统（客户机/服务器版）需求文档

> **课题来源**：《应用软件开发》课程开发课题三（详见PPT）
> **需求基线**：课题三功能与课题二完全相同，技术要求更高（C/S 架构）
> **文档性质**：需求整理稿，忠实转述课题原文并结构化；技术选型见同目录《TECHNICAL_DESIGN.md》，协作约定见根目录《CONTRIBUTING.md》

## 1. 项目概述

### 1.1 课题定位

实现一个健壮、易用的仓库管理系统，功能与课题二（桌面应用程序版）相同，但采用**桌面应用程序 + Web 应用程序组合**的客户机/服务器（C/S）方式实现。

**参考形态**（PPT 原文举例）：QQ、百度网盘、锐捷客户端、正版软件认证客户端——即"独立桌面程序 + 后台服务"的常见商业软件形态。

### 1.2 团队与组织约束

| 约束项 | 内容 |
|--------|------|
| 团队规模 | 2-3 人一组 |
| 分工硬性要求 | 每位成员至少独立完成以下一项：**多物料进仓、多物料出仓、权限管理、自动升级程序** |
| 阶段检查 | 第 6 周每人提交个人开发内容及小结 |
| 期末 | 小组及组员答辩（个人答辩一票否决）；无补考，只有重修 |
| 免答辩机会 | 第 7 周起可自主报名公开报告，报告的小组免期末答辩 |

## 2. 总体架构需求（课题三核心增量）

### 2.1 硬性架构要求

| 编号 | 要求 | 原文出处 |
|------|------|---------|
| AR-1 | 子系统 1-3 以**桌面程序（Windows 窗体程序）**实现 | 页 30 |
| AR-2 | 桌面程序以 **HTTP 方式**与后台 WEB 服务器进行数据通信 | 页 30 |
| AR-3 | **对数据库的操作由 WEB 服务器实现** | 页 30 |
| AR-4 | 桌面应用程序中**不得使用数据库的用户名和密码** | 页 30 |
| AR-5 | 桌面程序与 WEB 服务器之间的通信可使用 **RSA 加密（选做）** | 页 30 |
| AR-6 | 客户端无需保存数据库账号；**服务器端将数据库账号密码保存到配置文件中** | 页 30 |
| AR-7 | **修改业务逻辑不需要用户重装客户端** | 页 30 |
| AR-8 | 后台 WEB 服务器使用 TOMCAT（页 7 课题页明确点名） | 页 7 |

### 2.2 架构红线（PPT「开发中常见问题」页）

- ❌ **不得设计成 B/S 模式**（列为典型开发问题；客户端必须是桌面程序，不能做成网页/浏览器访问）
- ❌ 不得忽视质量要求（无事务处理、无异常处理、无正则表达式等）
- ❌ 各成员子系统无法集成（数据库、开发语言不统一）——开工前必须统一数据库与开发语言

### 2.3 职责边界

| 端 | 职责 |
|----|------|
| 客户端（桌面程序） | 界面展示、输入校验、发起 HTTP 请求；**不含任何数据库访问** |
| 服务端（Web 服务器） | 接收 HTTP 请求、执行全部数据库操作、返回结果；**唯一持有数据库凭证** |

## 3. 功能需求

功能编号规则：FR-子系统序号-序号。所有"程序/表/存储过程命名"要求见第 6 章命名规范。

### 3.1 子系统一：人员档案与物料档案管理（FR-1）

#### FR-1-1 主界面程序

- 包含主界面程序，**主界面可以通过菜单调用到其它所有子程序**。

#### FR-1-2 人员档案管理

**数据字段**：人员代码、姓名、性别、出生日期、身份证号、籍贯、家庭住址、联系电话、其它情况。

| 编号 | 需求点 |
|------|--------|
| FR-1-2-1 | 提供人员档案的增加、修改、删除程序（可合并为一个程序，也可分三个程序分别编程） |
| FR-1-2-2 | **人员代码不能为空** |
| FR-1-2-3 | 性别必须用「男 / 女」选择方式（单选/下拉），不允许自由输入 |
| FR-1-2-4 | 出生日期必须用**日期控件**控制 |
| FR-1-2-5 | 身份证号码最后一位可为数字或 X，**必须使用正则表达式进行验证** |
| FR-1-2-6 | 修改、删除操作前必须先进行**记录定位**，须提供相应查询程序，可借用查询程序完成定位 |
| FR-1-2-7 | 查询程序：输入人员姓名中的**任何一个单字**，可查询出含该字的所有人员 |

#### FR-1-3 物料档案管理

**数据字段**：物料代码、物料名称、规格型号、计量单位、库存数量、备注。

| 编号 | 需求点 |
|------|--------|
| FR-1-3-1 | 提供物料档案的增加、修改、删除程序（内容参考人员档案管理程序） |
| FR-1-3-2 | 物料代码**自动生成或手动输入**，不能为空，**不与现有代码重复** |
| FR-1-3-3 | 计量单位通过选择「件、套、公斤、吨、升、米、毫米、个」等，**并可输入其它单位名**（可选+可输入） |
| FR-1-3-4 | 库存数量默认为 0 |
| FR-1-3-5 | 查询程序：通过输入框文字对物料代码、名称、规格做**模糊查询**（是否含有该文字） |

### 3.2 子系统二：单物料进仓/出仓管理（FR-2）

每次进出仓**一种**物品。

**数据字段**：进出仓单号、进出仓日期、操作人员代码、经手人代码、备注、物料代码、进仓数量或出仓数量。

| 编号 | 需求点 |
|------|--------|
| FR-2-1 | 进仓程序与出仓程序可合并也可分开实现 |
| FR-2-2 | **操作人员默认为登录系统的当前用户**（不可随意填） |
| FR-2-3 | **经手人必须用下拉框选择** |
| FR-2-4 | **单号自动生成**，单号产生规则须在报告中说明 |
| FR-2-5 | 进出仓日期用日期控件 |
| FR-2-6 | **物料代码必须用下拉框选择** |
| FR-2-7 | 出仓时**必须判断出仓数量是否超过物料库存数量**（库存可从物料表获得） |
| FR-2-8 | 进出仓操作**必须通过调用存储过程实现**，存储过程将操作结果返回调用者，显示成功或失败信息 |
| FR-2-9 | 存储过程须判断：① 物料是否存在；② 操作后库存数量是否不为负数。不满足→显示失败提示；满足→增加进出仓表记录一条、按数量修改物料表库存、**提交**；否则**回滚** |
| FR-2-10 | 进出仓表可用一个表或两个表，**表设计思路须在报告中描述** |
| FR-2-11 | 进出仓单查询程序：支持进出仓日期**起止区间**、物料代码、操作人员、备注（**子串查询**）等条件 |

### 3.3 子系统三：多物料进出仓管理（FR-3）

一个进出仓单号上同时对**多种物料**做同进或同出操作（类比：淘宝一次买入多个不同商品）。

| 编号 | 需求点 |
|------|--------|
| FR-3-1 | 在一个界面、一个单号上同时完成多物料进仓或出仓操作 |
| FR-3-2 | **如果不成功，必须全部回滚**（整体成功或整体失败） |
| FR-3-3 | 多物料进仓/出仓可在一个程序中完成，也可分开编程 |
| FR-3-4 | 同一单号中：进出仓单号、进出仓日期、操作人员必须**完全相同** |
| FR-3-5 | 同一单号中**不能进仓与出仓同时存在**（同单同向） |
| FR-3-6 | 通过调用**存储过程**完成进出仓操作：多物料进出仓单增加到表中并修改多个物料库存数量，失败显示提示内容 |

### 3.4 子系统四：用户登录与权限管理（FR-4）

用户即操作人员（已在人员档案中管理）。每个**菜单项看作一个资源**。

| 编号 | 需求点 |
|------|--------|
| FR-4-1 | 人员表新增**口令字段**，口令在表内**加密存储** |
| FR-4-2 | 系统中每个操作人员都可以作为用户 |
| FR-4-3 | 用户权限修改时**不影响其他用户**；可对每个用户**单独授予**某个程序/菜单项的执行权，也可**单独收回**，而不影响其他用户 |
| FR-4-4 | 登录程序：输入用户名和口令，判断正确后**按用户权限显示有权的菜单项**；**无权菜单项必须不可见或不可操作** |
| FR-4-5 | **用正则表达式判断用户名和口令是否符合规则** |
| FR-4-6 | 用户授权程序：有授权权限的用户，可指定某用户获取某功能/菜单项执行权，或禁止其执行权 |
| FR-4-7 | 子系统四设计完成后，**可对后续新增的权限进行管理，而无需修改子系统四代码**（可扩展性硬性要求） |
| FR-4-8 | 登录程序要求安全稳定，需设计用户菜单及程序调用 |

### 3.5 子系统五：统计与报表（FR-5）

| 编号 | 需求点 |
|------|--------|
| FR-5-1 | 物料统计程序：统计各物料**指定时间内**的进出仓数量总数，用**图形显示**；并计算分析**流动量最小的物料** |
| FR-5-2 | 打印进出仓单程序：给定**月份**，将该月进出仓单全部**按单号顺序**打印 |
| FR-5-3 | 打印仓库账本程序：给定**年份和物料**，打印物料代码、名称、规格、计量单位、各日期的进仓、出仓和库存量 |
| FR-5-4 | 报表输出为 **PDF 文件或 Word、Excel 文件** |
| FR-5-5 | 报表必须包含**报表头、边框**，内容清楚、**排版合理**（PPT 附「规范的报表 / 不合格的报表」对照样例，页 27） |

### 3.6 补充功能：自动升级（FR-6）

| 编号 | 需求点 |
|------|--------|
| FR-6-1 | 应用程序运行时检测是否最新版本；若不是，提示用户升级，或自动升级 |
| FR-6-2 | PPT 给出两种实现方法（任选其一）：**方法一**——独立后台程序：自动启动，检测到主程序非最新版本，提示用户或自动下载最新版本替换旧版本；**方法二**——独立桌面升级程序：主程序启动后检测，非最新且用户同意更新→主程序启动升级程序→升级程序关闭主程序→下载主程序文件并替换→重新启动主程序→退出更新程序 |

### 3.7 可选功能（课题二层面的可选项）

| 功能 | 说明 |
|------|------|
| RSA 加密通信 | 课题三专属选做项（AR-5），加密桌面程序与服务器间的通信 |
| 操作日志 | 记录用户所做的数据库操作（课题二可选功能） |

## 4. 非功能性需求（质量要求）

PPT「质量要求」页（页 8）列出的考核维度，**更多要求见《团队工作质量自评表》**：

| 编号 | 质量维度 | 具体要求 |
|------|---------|---------|
| NFR-1 | 事务处理 | 是否该用、必用；处理方法的合理性（进出仓的提交/回滚即典型场景） |
| NFR-2 | 异常处理 | 处理时机、处理方式；**错误信息反馈的明确性** |
| NFR-3 | 人机界面设计 | 美观、易用性（对照 PPT 合格/不合格报表样例自查） |
| NFR-4 | 大数据表检索优化 | 数据表记录数很多时，当前处理方式效率如何？用何种方法优化？ |
| NFR-5 | 网络通信 | 加密与否；**数据封装效率**——XML、JSON、字符串的对比分析（课题三重点） |
| NFR-6 | 多用户并发冲突处理 | 同一功能多个用户同时使用时是否会出现问题？（如并发出仓超卖） |
| NFR-7 | 功能算法的时空优化 | 大量用户大量数据时，功能实现是否仍有较好性能 |
| NFR-8 | 复杂问题识别与方案设计 | 工程认证考核点：须识别课题主要复杂问题、提出**多个方案并比较择优**，且实现时采用最佳方案（不能只写不用） |

## 5. 数据需求

| 数据实体 | 关键字段 | 特殊约束 |
|---------|---------|---------|
| 人员档案 | 人员代码、姓名、性别、出生日期、身份证号、籍贯、家庭住址、联系电话、其它情况、（口令，子系统四新增） | 人员代码非空唯一；身份证号末位数字或 X（正则校验）；口令加密存储 |
| 物料档案 | 物料代码、名称、规格型号、计量单位、库存数量、备注 | 代码非空不重复；库存默认 0；单位可选项+自输入 |
| 进出仓单 | 单号、日期、操作人、经手人、备注、物料代码、数量（多物料场景拆主表+明细） | 单号自动生成（规则写入报告）；库存非负约束 |
| 用户-权限 | 用户、菜单项（资源）、授权关系 | 支持逐用户授予/收回；新增权限无需改代码 |

## 7. 交付与验收

### 7.1 考核构成

考勤、公开报告表现、阶段检查结果（第 6 周）、团队总体开发质量（工作质量自评表）、复杂问题识别与方案设计、文档质量（逻辑清楚、可读性好、总页数）、团队工作量自评（个人贡献：代码量、文档页数）、个人答辩（**一票否决**）。

### 7.2 验收自查要点

1. 架构红线：客户端是桌面程序、走 HTTP、零数据库凭证、非 B/S —— 四条逐条自查。
2. 功能演示：单字查人、正则校验（身份证/用户名/口令）、下拉选择（经手人/物料/单位）、日期控件、单号规则说明、多物料整体回滚、无权菜单不可见、报表头+边框排版。
3. 并发与性能演示：双客户端并发出仓冲突场景、大数据量分页检索效率对比。
4. 报告必备内容：单号生成规则、进出仓表设计思路（一表 vs 两表）、通信封装效率对比（XML/JSON/字符串）、复杂问题识别与多方案比较择优。

### 7.3 风险提示（PPT 列举的典型失败模式）

- 忽视质量要求（无事务、无异常处理、无正则）
- 设计成 B/S 模式
- 个别成员无贡献
- 成员间缺乏沟通 → 子系统无法集成（数据库、开发语言不一致）
- 到期末才要求换课题、小组因矛盾散伙
